# Módulo de clientes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. A escolha da execução pertence ao usuário. As instruções do projeto sobre não criar/executar testes prevalecem sobre o fluxo padrão dessas habilidades.

**Goal:** Entregar cadastro completo de clientes PF/PJ com tabela, modais, endereço inicial opcional e gerenciamento de endereços.

**Architecture:** Concentrar o módulo em `frontend/src/pages/Customers`, separando página, formulário, campos compartilhados de endereço, gerenciamento e funções de dados/filtros. Reutilizar os componentes existentes e enviar cliente com endereço opcional na mesma requisição transacional. Alterar a API somente para permitir limpar e-mail e WhatsApp na edição.

**Tech Stack:** React, Vite, Tailwind, lucide-react; API Spring Boot/PostgreSQL existente.

**Spec:** `docs/superpowers/specs/2026-10-10-clientes-design.md` — documento aprovado pelo usuário.

## Restrições globais

- Não criar nem executar testes automatizados, build ou lint por padrão, conforme as preferências do projeto. Fazer revisão direta das alterações e conferir o diff sem afirmar validação em execução.
- Usar React e Tailwind já instalados. Reutilizar `Modal`, `Dropdown`, `api` e ícones pelos nomes originais de `lucide-react`.
- Ficam fora desta versão: exclusão de clientes, seleção/gestão de tabelas de preços, integração com pedidos, consulta automática de CEP, novas bibliotecas e validação de dígitos verificadores de CPF/CNPJ.
- Preservar alterações preexistentes no projeto. Não incluir outros módulos nem migrações existentes nas mudanças ou em commits desta implementação.
- Executar as tarefas em ordem; dependem dos contratos definidos na tarefa anterior.

## Pontos prioritários da revisão direta

1. Endereço desativado deve ser omitido; ativado e incompleto deve bloquear envio; falha no POST deve preservar todo o formulário.
2. PATCH parcial deve preservar dados omitidos, permitir limpar e-mail/WhatsApp e não apagar campos ocultos na troca PF/PJ.
3. Pesquisas contendo somente pontuação não devem coincidir com todos os documentos/telefones por comparação com string vazia.
4. Falha no carregamento de endereços não deve oferecer cadastro como se não houvesse endereços; tipos duplicados devem ficar indisponíveis.
5. Uma gravação bem-sucedida seguida de falha ao atualizar a lista não deve deixar o formulário pronto para repetir a criação.

### Tarefa 1: Contrato de edição e funções do módulo

**Arquivos:** modificar `CustomerService.java`; criar `customerConfig.js` e `customerFilters.js` nos caminhos acima.

**Interfaces produzidas:**

- `PERSON_TYPE_OPTIONS`, `ADDRESS_TYPE_OPTIONS`, `CUSTOMER_LIMITS`, `ADDRESS_FIELDS`: opções `{value, label}`, limites por propriedade e descritores `{name, label, maxLength}`.
- `createCustomerForm(customer = null) -> object`: campos de cliente como texto, PF por padrão, `includeAddress: false` e `address` inicial com tipo MAIN. Na edição, guardar a data original em `originalBirthDate` para explicar a preservação quando o campo for esvaziado.
- `createAddressForm(address = null) -> object`: campos de endereço como texto e tipo MAIN por padrão.
- `buildCustomerPayload(form, { editing = false } = {}) -> object`: dados normalizados, sem `priceTableId`; campos pertinentes a PF/PJ; `address` apenas no cadastro com `includeAddress` ativado. Omitir data vazia na edição e preservar campos ocultos por omissão.
- `buildAddressPayload(form) -> object`: tipo e campos de endereço sem `customerId`, aparando espaços.
- `validateCustomerForm(form, { editing = false } = {}) -> string` e `validateAddressForm(form) -> string`: retornar mensagem em português ou string vazia. Conferir obrigatórios, limites, e-mail opcional, data preenchida válida e campos do endereço quando ativado.
- `filterCustomers(customers, { search, personType, active }) -> array`: pesquisa e filtros combinados; `active` usa `""`, `"true"` ou `"false"`.

- [x] No `CustomerService.update`, aceitar e-mail/WhatsApp não nulos, convertendo string vazia/branca em `null`, e preservar valores quando a propriedade não for enviada ou for `null`.
- [x] Criar opções PF/PJ, Principal/Cobrança/Entrega e limites: nome/nome fantasia/e-mail 150, documento 14, telefone/WhatsApp/inscrições 20; endereço: estado 50, cidade/bairro/complemento 100, rua 150, número 10 e CEP 9.
- [x] Implementar criação dos estados e construção dos dados, removendo pontuação de documento e telefones e aparando textos. Não forçar remoção dos dados ocultos ao trocar tipo na edição.
- [x] Implementar validação dos dados enviados: nome/documento/telefone, nome fantasia para PJ; e-mail quando preenchido; endereço completo quando ativado, incluindo complemento.
- [x] Implementar filtros textuais sem diferença de caixa e pesquisa de números sem pontuação, condicionando comparação numérica a uma busca normalizada não vazia.
